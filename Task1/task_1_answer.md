# Задание 1. Исследование моделей и инфраструктуры

## 1. Сравнение инструментов

### 1.1. Сравнение LLM-моделей

Рассматриваемые варианты:

- локальные open-source модели из Hugging Face: Qwen, Llama, Gemma, Mistral, DeepSeek и аналогичные модели;
- облачные модели: OpenAI и YandexGPT.

| Критерий                           | Локальные Hugging Face / open-source модели                                                                                                                                                                                                                         | Облачные OpenAI / YandexGPT                                                                                                                                                                                                              |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Качество ответов                   | Качество зависит от конкретной модели, ее размера, языка документации и качества настройки. Для простых внутренних вопросов локальная модель может быть достаточной, но на сложных архитектурных и аналитических запросах обычно уступает сильным облачным моделям. | Главное преимущество облачных моделей - более высокое и стабильное качество ответов на старте. Они лучше подходят для прототипа, потому что позволяют быстрее проверить гипотезу без долгого подбора и настройки собственной модели.     |
| Скорость работы                    | Скорость зависит от GPU, размера модели и числа одновременных пользователей. При росте нагрузки придется самостоятельно масштабировать инфраструктуру: добавлять GPU, настраивать балансировку, очереди, мониторинг и резервирование.                               | На старте обычно проще получить приемлемую скорость. Но нужно уточнять SLA, лимиты, доступность региона, задержки и условия масштабирования. При росте нагрузки большую часть инфраструктурного масштабирования берет на себя провайдер. |
| Стоимость владения и использования | На малой нагрузке локальная установка часто дороже из-за серверов, GPU, администрирования и поддержки. На масштабе локальная установка может стать выгоднее, потому что нет оплаты за каждый запрос и каждый токен.                                                 | Для прототипирования обычно выгоднее: не нужно покупать GPU и строить MLOps-инфраструктуру. Но при высокой постоянной нагрузке стоимость API может стать выше, чем стоимость собственной локальной установки.                            |
| Удобство и простота развертывания  | Сложнее: нужно выбрать модель, подготовить серверы, настроить inference, безопасность, мониторинг, обновления и отказоустойчивость.                                                                                                                                 | Выигрывает по удобству: достаточно подключить API, настроить ключи, лимиты и интеграцию с приложением. Это лучший вариант для быстрого запуска.                                                                                          |
| Ограничения по данным              | Лучше подходит для конфиденциальных документов, которые нельзя отправлять внешним провайдерам.                                                                                                                                                                      | Подходит для неконфиденциальных данных и быстрого прототипа. Для чувствительных материалов нужны юридическая проверка, условия обработки данных, SLA и требования к региону хранения/обработки.                                          |

### 1.2. Сравнение моделей эмбеддингов

Рассматриваемые варианты:

- локальные Sentence-Transformers;
- облачные OpenAI Embeddings.

| Критерий                           | Локальные Sentence-Transformers                                                                                                                                                                                                       | Облачные OpenAI Embeddings                                                                                                                                              |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Скорость создания индекса          | Для пилота можно использовать CPU, но для первичной индексации большого объема документов лучше иметь GPU. После первичной индексации прирост документов небольшой относительно общего объема, поэтому нагрузка будет контролируемой. | Индекс создается быстро, так как вычисления выполняются на стороне провайдера. Ограничения связаны с лимитами API, сетью и стоимостью обработки большого объема текста. |
| Качество поиска                    | Хорошее, если выбрать многоязычную модель, подходящую для технической документации. Качество нужно проверять на реальных вопросах сотрудников.                                                                                        | Обычно высокое и стабильное качество, хорошее решение для быстрого прототипа и эталонного сравнения.                                                                    |
| Стоимость владения и использования | Нет оплаты за каждый токен, но есть расходы на сервер, поддержку и переиндексацию. Для большого объема внутренних документов и регулярной переиндексации может быть выгоднее облака.                                                  | Удобно и дешево на старте, но стоимость зависит от объема индексируемого текста. Для закрытых документов может быть недопустимо отправлять текст во внешний API.        |
| Удобство внедрения                 | Требует выбора модели, настройки окружения и контроля версий индекса.                                                                                                                                                                 | Проще внедрить: API уже готов, не нужна локальная модель и отдельный GPU.                                                                                               |

### 1.3. Сравнение ChromaDB и FAISS

| Критерий                                   | FAISS                                                                                                                                               | ChromaDB                                                                                                                                                                                                          |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Скорость поиска и индексации               | Очень быстрый векторный поиск.    | Достаточно быстрый для RAG-сценариев, но это более прикладная база с дополнительными возможностями, поэтому эксплуатационно она сложнее простого FAISS-индекса.                                                   |
| Сложность внедрения и поддержки            | Простое внедрение для MVP. Основная сложность появится позже: отдельно нужно хранить метаданные, права доступа, версии документов и версии индекса. | Чуть сложнее старт, зато удобнее для дальнейшего развития: есть коллекции, хранение документов и метаданных, фильтрация, server/client режимы.                                                                    |
| Удобство в работе                          | Хорош как быстрый низкоуровневый индекс. Менее удобен как полноценная база знаний, потому что часть функций нужно реализовывать вокруг него.        | Удобнее как готовая RAG-база: проще работать с документами, метаданными, фильтрами и несколькими коллекциями.                                                                                                     |
| Стоимость владения с учетом инфраструктуры | Для MVP дешевле: можно запустить вместе с ботом и хранить индекс на локальном volume. Не требует отдельного сервиса и отдельной команды поддержки.  | Open-source вариант бесплатный, но отдельный сервис требует больше сопровождения: хранение, бэкап, мониторинг, обновления, сетевой доступ и права.  |
| Масштабирование                            | Для масштабирования нужно самостоятельно проектировать шардирование, обновление индекса, бэкап и интеграцию с БД с метадатой.                          | Лучше подходит для перехода к production-системе, если нужны управляемые коллекции, фильтрация и более удобная эксплуатация.                                                                                      |

## 2. Варианты решения

### Вариант A. Быстрый облачный прототип

| Компонент  | Выбор                              |
| ---------- | ---------------------------------- |
| LLM        | OpenAI или YandexGPT               |
| Embeddings | OpenAI Embeddings                  |
| Vector DB  | FAISS                              |
| Сервер     | 4-8 vCPU, 16-32 GB RAM, SSD 256 GB |
| GPU        | Не требуется                       |

Плюсы:

- самый быстрый запуск;
- минимальная собственная инфраструктура;
- удобно проверить гипотезу на неконфиденциальных данных;
- облачный провайдер берет на себя масштабирование LLM-инфраструктуры.

Минусы:

- нельзя использовать чувствительные документы без юридической и compliance-проверки;
- есть зависимость от провайдера, SLA, лимитов и региона обработки данных;
- при большой постоянной нагрузке стоимость API может стать высокой.

### Вариант B. Гибридный пилот

| Компонент  | Выбор                                                                                             |
| ---------- | ------------------------------------------------------------------------------------------------- |
| LLM        | Облачная модель для прототипа; локальная модель для чувствительных данных после проверки гипотезы |
| Embeddings | Локальные Sentence-Transformers                                                                   |
| Vector DB  | FAISS                                                                                             |
| Сервер     | 8-16 vCPU, 32-64 GB RAM, NVMe SSD 512 GB                                                          |
| GPU        | Опционально 1 GPU 16-24 GB VRAM                                                                   |

Плюсы:

- хороший баланс скорости запуска, стоимости и контроля данных;
- можно начать с облачной LLM и постепенно переносить часть нагрузки локально;
- локальные embeddings снижают риск передачи внутренних документов наружу;
- FAISS позволяет быстро собрать MVP без отдельной vector DB-инфраструктуры.

Минусы:

- сложнее, чем полностью облачный прототип;
- нужно поддерживать локальный индекс и процесс переиндексации;
- нужно заранее разделить документы на конфиденциальные и неконфиденциальные.

### Вариант C. Полностью локальная установка

| Компонент  | Выбор                                                     |
| ---------- | --------------------------------------------------------- |
| LLM        | Локальная open-source модель                              |
| Embeddings | Локальные Sentence-Transformers                           |
| Vector DB  | ChromaDB                                        |
| Сервер     | 16-32 vCPU, 128 GB RAM, NVMe SSD 1 TB                     |
| GPU        | 1-2 GPU с 48-80 GB VRAM или несколько GPU меньшего объема |

Плюсы:

- максимальный контроль над данными;
- потенциально выгоднее при большой постоянной нагрузке;
- меньше зависимость от внешних API и внешних SLA.

Минусы:

- высокая стоимость старта;
- сложная эксплуатация и масштабирование;
- качество локальной модели нужно отдельно сравнивать с облачными моделями.

### Вариант D. Production cloud-first

| Компонент  | Выбор                            |
| ---------- | -------------------------------- |
| LLM        | OpenAI или YandexGPT             |
| Embeddings | OpenAI Embeddings                |
| Vector DB  | ChromaDB                         |
| Сервер     | 8-16 vCPU, 32 GB RAM, SSD 256 GB |
| GPU        | Не требуется                     |

Плюсы:

- быстрее развивать систему после прототипа;
- меньше собственной ML-инфраструктуры;
- проще масштабировать нагрузку на LLM и embeddings;
- ChromaDB удобнее для дальнейшей эксплуатации, чем простой FAISS-индекс.

Минусы:

- зависимость от провайдера, SLA, лимитов и стоимости API;
- требуется отдельная проверка требований к хранению и обработке данных;
- не подходит для документов, которые нельзя передавать внешнему провайдеру.

## 3. Рекомендуемая конфигурация сервера

Для первого рабочего пилота лучше выбрать вариант B - гибридный пилот.

Рекомендуемая конфигурация:

- CPU: 8-16 vCPU;
- RAM: 64 GB;
- диск: NVMe SSD 512 GB;
- GPU: опционально 1 GPU с 24 GB VRAM;
- запуск: Docker Compose;
- векторная база: FAISS;
- embeddings: локальные Sentence-Transformers;
- LLM: облачная модель на этапе прототипа, затем гибридная схема с локальной моделью для чувствительных данных.

Такой сервер достаточен для пилота на базе знаний текущего размера. На старте можно не покупать дорогой GPU-кластер, но оставить возможность добавить GPU для локальных embeddings и локальной LLM.

## 4. Итоговая рекомендация

Итоговый выбор для проекта:

- векторная БД: FAISS;
- embeddings: локальные Sentence-Transformers;
- LLM: облачная OpenAI или YandexGPT для прототипа на неконфиденциальных данных;
- дальнейшее развитие: гибридная схема с локальной LLM для чувствительных данных и высокой регулярной нагрузки.

Почему выбран FAISS:

- он проще и дешевле для MVP;
- хорошо интегрируется с LangChain;
- не требует отдельного сервиса и отдельной инфраструктуры;
- подходит для быстрой проверки качества RAG-бота;
- его достаточно для первого пилота при текущем объеме базы знаний.

Почему не ChromaDB на первом этапе:

- ChromaDB удобнее для production и работы с метаданными, но для первого MVP добавляет лишний инфраструктурный слой;
- на старте важнее быстро проверить гипотезу, качество поиска и стоимость эксплуатации;
- если требования к фильтрации, правам доступа и управлению коллекциями станут критичными, миграцию на ChromaDB можно выполнить после пилота.

Лучшая стратегия для QuantumForge: сначала гибридный пилот с FAISS и локальными embeddings, затем постепенный переход к более зрелой production-архитектуре на основе фактической нагрузки, требований безопасности и результатов тестирования качества.
